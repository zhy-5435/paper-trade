# 附录：高性能撮合演进（面试知识扩展）

> **边界说明**：本文为高性能撮合的知识扩展与远期演进参考，**不属于本项目当前实现范围**。项目定稿（见 [01-需求与边界](../design/01-需求与边界.md)、[02-架构设计](../design/02-架构设计.md)）采用单机简化版撮合：内存盘口 + DB 顺序日志重放（简化版事件溯源），不引入 Disruptor/红黑树，性能目标为下单 TPS≥100 而非百万级。本文方案不进入当前代码与技术栈。

## 百万级 TPS 撮合：传统方案痛点
Tomcat 多线程订单直接写 MySQL，并发线程争抢锁，TPS 过千后磁盘 IO 打满、锁竞争，系统雪崩。

## 整体思路：拒绝 MySQL，纯内存计算 + 事件溯源保证不丢单
1. **事件溯源（MQ 持久化日志）**：外部请求统一转为有序操作日志追加写入 MQ（Kafka/RocketMQ）；MQ 相当于账本，引擎只做内存计算，断电后回放日志重算，防止丢单。
2. **Disruptor 无锁单线程**：不用 JDK 阻塞队列（加锁性能差），依靠 RingBuffer、CAS 无锁、消除伪共享；并发洪峰漏斗收敛为单线程串行消费，消除锁与上下文切换，支撑百万 TPS。
3. **红黑树 + 订单链表**：红黑树按价格排序（买盘倒序最高价在根、卖盘正序最低价在根），同价位挂链表保证时间优先；新订单在对手盘匹配最优价，满足即成交，不交叉则盘口静止。
4. **快照 + 增量回放**：定时对内存盘口打快照落盘；宕机恢复加载最近快照 + 回放快照后少量 MQ 增量日志，几秒内重建。

## 组合拳
事件溯源 + Disruptor 无锁单线程消费 + 红黑树买卖盘 + 定时快照与增量回放。

> 与本项目的衔接：本项目「盘口可丢、以 deal_record/trade_order 为权威重建」的可靠性思路与事件溯源同源，只是用 DB 回放替代 MQ 日志回放，体量可控。
