## 三、资金与记账正确性

### FUN-01【P0 · 确认】分笔最低佣金与整单冻结预留不一致

- **位置**：`OrderServiceImpl.java:108-109`（freezeAmount = 金额 + `buyFeeEstimate(整单金额)`）；`FeeCalculator.java:18-21`（commission = max(金额×费率, 5)）；`DealBookingService.bookBuy:88-94`（每笔成交各收一次 commission）；`AccountServiceImpl.fee:139-142`（仅 requirePositive，不校验余额）；`sql/schema.sql:102,130`（CHECK `frozen_amount <= balance`，资金流水同样约束）。
- **问题**：下单只按整单预留一次最低 5 元佣金，但每笔成交各收一次最低 5 元。对手分 N 笔成交时实际佣金 ≥ N×5 > 预留 5 元。
- **复现算例**（已按代码逐步推演）：买 200 股 @10，冻结 2005（2000 + 预估佣金 5），账户余额恰 2005。第一笔成交 100 股：按比例解冻 2005×100/200 = 1002.50，`deduct` 后 balance=1005、frozen=1002.50（CHECK 通过）；随后 `fee(5)` 使 balance=1000 < frozen=1002.50，**违反 `chk_account_amount` 与 `chk_fund_flow_balance`** → DataIntegrityViolationException → 整笔事务回滚。该失败是确定性的，顺序消费重试 5 次（`max-reconsume-times: 5`）耗尽进死信；卖方独立消费可能已入账减仓，形成单边账（衔接 FUN-02）。
- **补充事实**：`fee()` 确实不校验可用余额，完全靠 DB CHECK 兜底；卖方 `sellFee` 按成交金额封顶（`FeeCalculator.java:28-30`）安全。原 A-21 中"舍入导致负解冻"的推演不成立（见第六节第 1 条），本条的真正缝隙就是最低佣金口径。
- **建议**：冻结时按"可能拆分的最大笔数"预留佣金上界，或改为整单佣金在最后一笔成交时一次性结算（分笔只按比例扣金额），或成交佣金低于最低值时按剩余额度收取并在订单终态统一补差；同时 `fee()` 增加可用余额前置校验，把确定性失败挡在消费之前。

### FUN-02【P0 · 部分确认（时序修正）】单侧记账失败无冲正闭环，补偿窗口有限，订单永久卡死

- **位置**：`DealBookingService.consumeBuy/consumeSell:56-73`（买卖独立消费）；`DealCompensateTask.java:43-65`（只比对 B5/S6 流水缺失即补发，不检查订单状态；窗口 `compensate-window-minutes: 10`，周期 60s）；`OrderCancelService.expireOne:153` 与 `assertNoInFlight:183-188`（Σdeal_qty == matched_qty 在途检查）；`BuyDlqAlarmConsumer/SellDlqAlarmConsumer`（仅 log.error）。
- **确认的部分**：
  - 买卖两侧独立事务消费，一侧确定性失败（如 FUN-01）时另一侧可能已入账，**无记账状态表、无冲正/补记闭环**。
  - 补偿任务只按流水缺失重发同一条必然失败的消息，10 分钟窗口过后连重发也停止；覆盖不了"故障超过 10 分钟"的场景。
  - 补偿确实不检查订单状态（消费端幂等前置 `alreadyBooked` 只能保护"已记账"的重放，保护不了"未记账 + 订单终态"）。
- **修正的部分（原 A-3 时序不成立）**：异步模式 T2' 只落 deal_record（`DealFactService.java:33-55`），`matched_qty` 只在记账成功时更新。因此**只要记账缺失，Σdeal_qty > matched_qty 恒成立**，日切 `expireOne` 与用户撤单的在途检查都会**跳过**该订单，而不是"检查通过 → 误置 EXPIRED → 之后补偿 MATCH_CONFLICT"。
- **实际后果（比原描述更隐蔽）**：记账永久缺失的订单**永远无法过期/撤销**（每次日切都被在途检查跳过），永久滞留盘口；deal_record 有成交、资金/持仓无记账，三方对账必然差异且无任何自动修复路径（无运行时对账，见 OBS-01）。
- **建议**：建立"记账状态表 + 确定性失败识别 + 告警 + 人工补记/反向冲正"闭环；补偿任务区分可重试/确定性失败，确定性失败停止无意义重发并升级告警；补偿窗口改为"扫描所有未记账成交"而非固定时间窗。

### FUN-03【P2 · 部分确认（后果降级）】upsertDaily 读-改-写无并发保护

- **位置**：`DealBookingService.upsertDaily:157-180`（先 select 再 insert/update，无 DuplicateKeyException 捕获，updateById 无 version 条件）；`sql/schema.sql:329`（`uk_user_date_order` 唯一键存在）。
- **确认的部分**：读-改-写模式与缺失的防护属实。且事务消息**不带分片键**（`DealMessageProducer.java:16-17`，RocketMQ 事务消息轮询选队列），同订单多笔成交可落入不同队列被并发消费，并发窗口真实存在。
- **降级的原因**：`upsertDaily` 与订单 version CAS（`transitOrder:152`）在**同一事务**，且订单 UPDATE 的行锁使两个并发事务无法同时通过 CAS——只有一个能提交，另一个整体回滚重试。因此原描述的"双 insert 冲突后整笔回滚"会以 CAS/行锁冲突形式出现，但**"后写覆盖前写、日汇总少计一笔"的已提交丢失更新不会发生**。
- **实际影响**：高并发下冲突重试消耗（顺序消费重试上限 5 次，极端竞争下有进死信风险）；正确性依赖"订单 CAS 恰好兜住日汇总"这一隐式串行化，脆弱。
- **建议**：防御性补齐——insert 捕获 DuplicateKeyException 转 update，update 带 version 或改 `SET deal_qty = deal_qty + ?` 原子累加，消除对隐式串行化的依赖。

## 四、撮合与订单生命周期

### MAT-01【P1 · 确认】撮合触发丢失无兜底，挂单永久滞留

- **位置**：`MatchEngine.onOrderCreated:85-92`（异常只打日志）；`onNewOrder:94-107`（tryLock 3s 超时/中断直接 return，注释"留单待下次触发"）；`executeWithRetry:156-182`（重试耗尽/不可重试异常 break 留单）；全工程仅两个 `@Scheduled`（QuoteRefreshTask、DealCompensateTask），**无周期性盘口扫描任务**。
- **问题**：同股票若无后续新订单，就没有"下次触发"。MQ 宕机、锁竞争、DB 抖动、AFTER_COMMIT 事件前进程崩溃，都会让本可成交的挂单滞留盘口，只有重启重建或同股新单才能救活。
- **关联**：A-28 的"复牌后停牌挂单不自动恢复撮合"（`StockServiceImpl.updateStatus:128-142` 不触发任何撮合）是同一根因的另一表现，合并于此。
- **建议**：增加周期性"扫描有挂单的盘口重新撮合"任务（拿股票锁后调 matchLoop）；复牌（updateStatus → 1）时主动触发一次该股撮合。

### MAT-02【P1 · 确认】自成交防护造成队头阻塞，与 README 口径不符

- **位置**：`MatchEngine.matchLoop:137-140`（bestBid 与 bestAsk 同用户时 `break`）；`README.md:18`（写的是"自成交/停牌**跳过**"）。
- **问题**：队头一对自成交单直接停止整个撮合循环，后面所有**其他用户**的可成交对都被挡住。停牌 break 是对的（整股停撮），自成交 break 是错的。
- **建议**：跳过该对继续撮合下一档（如跳过该 ask 取次档 ask，或按业务口径跳过该 bid），并同步修正 README 措辞。

### MAT-03【P1 · 确认】委托过期时间不生效，跨日挂单可复活成交

- **位置**：`BookOrder.java`（无 expireTime/tradeDate 字段）；`MatchEngine.matchLoop:126-154`（只判价格/自成交/停牌，不看 expire_time）；`MatchEngine.rebuild:66-83`（只按状态 PENDING/PARTIAL_FILLED 重建，不过滤 trade_date/expire_time）。
- **问题**：expire_time（下单时设为 tradeDate 15:00，`OrderServiceImpl.java:221`）只是展示字段。15:00 后到日切执行前挂单仍可成交；若订单因在途检查被日切跳过（FUN-02），上一日挂单下一日继续参与撮合。重启重建同样复活过期单。
- **建议**：matchLoop 与 rebuild 增加 expire_time/trade_date 过滤；过期单触发过期撤单流程而非静默跳过。

## 五、日切与清算

### SET-01【P0 · 确认】日切不幂等可重跑：closeDate 任取、无批次状态

- **位置**：`SettlementService.currentQuoteTradeDate:101-104`（`LIMIT 1` 任取一条行情的 trade_date）；`run:83-95`（每次重新推导 closeDate，无批次记录）；`cutQuotes:123-135` 与 `cutOneQuote:137-166`（逐股独立事务提交，3 次 CAS 失败抛 SYSTEM_BUSY 中断整批）；`sql/schema.sql:250`（settlement_batch 表存在，代码注释明确"不写 settlement_batch"）。
- **问题**：
  1. 第一次日切 D→D+1 成功后再点一次，closeDate 取到 D+1 → 变成 D+1→D+2：`expireOrders` 把新一天的订单全部过期，`clearTodayBuy` 再清一次，行情再推进一天。**"幂等可重跑"只对 cutQuotes 单股成立，对整次日切不成立**。
  2. cutQuotes 中途失败后各股 trade_date 分叉（部分 D、部分 D+1），重跑时 `LIMIT 1` 取到哪条不确定，closeDate 随之漂移，分叉无法收敛。
  3. leader 锁只防并发，不防顺序重跑。
- **建议**：以 settlement_batch（或等价批次状态）记录"目标收盘日 + 各步骤进度"，重跑按批次恢复而非重新推导 closeDate；closeDate 改为取 MIN(trade_date) 或显式入参；整批完成前拒绝新批次。

### SET-02【P1 · 确认】clearTodayBuy 与在线记账无隔离，T+1 可被击穿

- **位置**：`SettlementService.clearTodayBuy:169-173`（全表 `UPDATE ... SET today_buy_qty=0 WHERE today_buy_qty>0`，无 version、不落流水）；`PositionServiceImpl.addOnBuy:139-147`（带 version CAS）；日切全程无停牌/停撮合闸门。
- **问题**：清零 UPDATE 不走乐观锁也不 bump version，与并发买入成交双向竞争：
  - addOnBuy 先提交、清零后执行 → **清零瞬间的新成交 today_buy 被一并清掉，当日买入变当日可卖，违反 T+1**；
  - 清零先执行、addOnBuy 后提交（其 CAS 因 version 未变仍成功）→ 旧 today_buy 被复活，次日可卖数量错误减少。
  - 跨日成交还会按订单旧 trade_date 记日汇总（与 CAC-03 叠加）。
- **备注**："不落流水"是设计文档 03§四.7 的既定口径，本身不是 bug；竞争窗口才是。
- **建议**：日切在停撮合闸门内执行（或清零语句带 version/条件限定 trade_date）；至少在日切期间拒绝该股新撮合。

## 六、缓存与行情

### CAC-01【P1 · 确认】布隆假阴性误拒真实股票，无法自愈

- **位置**：`StockServiceImpl.createStock:96`（bloomAdd 失败仅 warn 忽略，`RedisCacheClient.bloomAdd:126-133`）；`getStock:57-70` / `QuoteServiceImpl.getQuote:56-75`（布隆判无直接抛 1001，走不到 DB 回源处的 bloomAdd 补加点）；`StockCacheInitializer:37-45`（仅启动时装入全部代码）。
- **问题**：新增股票时 Redis 抖动导致 bloomAdd 失败，过滤器存在但缺该代码 → 读路径在布隆处直接返回"股票不存在"(1001)，**永远走不到 DB 回源补加**，只能重启（或手工删过滤器 key）恢复。注意这不是布隆的"假阳性"，而是**加入失败造成的真阴性丢失**。
- **建议**：bloomAdd 失败时补偿重试/异步补加；或读路径判无后仍回源 DB 确认一次（DB 存在则补加布隆并放行），把布隆降级为纯加速器。

### CAC-02【P1 · 确认】股票缓存 30 分钟 + 撮合旧快照，停牌状态陈旧

- **位置**：`application.yml:74`（stock-ttl-ms: 1800000）；`StockServiceImpl.updateStatus:140-141`（evictDelayedDouble：立即删 + 1s 延迟删，`RedisCacheClient:94-101`，删除失败仅 warn）；`MatchEngine.matchLoop:127`（循环开始前取一次 stock 快照，且 getStock 本身读缓存）。
- **问题**：
  1. "删除后回填旧值"窗口：慢读在更新前取 DB 旧值、在两次删除之后写缓存 → 陈旧最长 30 分钟；Redis 故障时删除失败仅 warn，同样陈旧 30 分钟。期间撮合继续交易停牌股。
  2. 停牌生效瞬间，正在进行的 matchLoop 用旧快照仍可继续成交数笔。
- **备注**：原 A-28 "updateStatus 无事务"的说法不构成核心问题——单条 UPDATE 本身原子；核心是无撮合触发（已并入 MAT-01）与本条的状态陈旧。
- **建议**：matchLoop 每笔成交前以 DB 为准复核股票状态（或停牌变更走股票锁 + 版本号）；缓存回填带版本/短 TTL；删除失败升级为告警并主动失效。

### CAC-03【P1 · 确认】下单用缓存行情做关键校验，订单出生即可能过期

- **位置**：`OrderServiceImpl.createOrder:97-101`（用 `quoteService.getQuote` 校验涨跌停）、`:209/:221`（tradeDate/expireTime 取自该 quote）；`QuoteServiceImpl.getQuote:60-74`（Redis 缓存 TTL 3s±1s）；`SettlementService.run:92`（日切后 deleteByPattern 失败仅告警忽略，`RedisCacheClient:85-91`）。
- **问题**：日切刚完成、缓存未失效完时，订单带着**昨天的 tradeDate 和昨天的涨跌停价**创建。Q12 的 `trade_date<=` 扫描（`expireOrders:107-112`）只能保证它最终被过期，订单从出生起就是过期单。写路径读缓存做关键校验，违反"MySQL 始终为权威"的自家原则（`RedisCacheClient` 头注）。
- **建议**：下单路径的涨跌停/tradeDate 改读 DB（或缓存 miss 强制回源 + 日切后强校验 tradeDate），读路径继续用缓存。

### QUT-01【P1 · 确认】行情刷新与成交量额共用 version，撞行回滚成交事实

- **位置**：`QuoteServiceImpl.refreshOne:130-156`（每 3s 一次，**不拿股票锁**，CAS stock_quote.version）；`accumulateDeal:114-128`（T2' 内同样 CAS 同一 version）；`DealTransactionListener.executeLocalTransaction:44-56`（落库异常 → ROLLBACK → F1）；`MatchEngine.executeWithRetry`（F1 换新 dealNo 重试 ≤3 次）。

## 七、基础设施与可用性

### INF-01【P1 · 确认（口径修正）】限流器 Redis 丢数据后永久 5001，且无故障降级

- **位置**：`RateLimitAspect.java:25,46-52`（本地 `initializedKeys` 认为已初始化就不再 setRate）；`RateLimiterClient.java:22-29`（setRate/tryAcquire 均无异常捕获）；`GlobalExceptionHandler:78-82`（未捕获异常统一 5001）。
- **问题**：
  1. Redis 重启/驱逐丢掉限流器 key 后，本地标记仍认为已初始化，不再 setRate；Redisson 对未初始化限流器 tryAcquire 抛异常 → **该用户该维度永久 5001，直到应用重启**。
  2. Redis 完全故障时，所有带 `@RateLimit` 的端点（下单、批量行情）在切面层即失败，无降级放行。
- **口径修正**：原 B-P1-5 "批量行情在 Redis 故障时不再降级读 DB"的说法不准确——`batchQuotes:86-93` **恒读 DB、从不走缓存**；真正的阻塞点是限流切面无 Redis 故障降级，请求到不了 DB 层。缓存读路径本身降级是完善的（get 失败回源、布隆按不确定放行）。
- **建议**：tryAcquire 捕获"未初始化"异常后重新 setRate 再试；Redis 故障时限流降级放行（或本地兜底限流）并告警。

## 十一、核实修正与排除（原意见中不成立或需修正的描述）

1. **【不成立】A-21"部分成交 HALF_UP 舍入累计多解冻 → 最后一笔为负 → PARAM_ERROR 永久死信"**
   数学上不可复现：每笔解冻 = round2(frozen × qty/remain)，qty < remain 且 frozen 恒为整分值，故单笔解冻 ≤ 当前 frozen，frozen 永不减为负；最后一笔解冻"剩余 frozen"≥ 0，总解冻恒等于初始冻结。`deduct` 的负值校验（`AccountServiceImpl:124-126`）不会被该路径触发。A-21 中成立的部分（fee 不校验余额、卖方封顶安全）已并入 FUN-01。
2. **【修正】A-3"日切在途检查此刻相等 → 误置 EXPIRED → 补偿到达 MATCH_CONFLICT 再进死信"**
   matched_qty 只在记账成功时更新（T2' 只落 deal_record），记账缺失时 Σdeal_qty > matched_qty 恒成立，`expireOne:153` 与 `assertNoInFlight` 都会跳过而非放行。真实后果是订单**永久卡死 + 单边账永久缺失**（FUN-02），比"误过期"更隐蔽但同样严重。"补偿不查订单状态、10 分钟窗口覆盖不足"属实。
3. **【降级】A-9"双 insert / 后写覆盖前写 → 日汇总少计一笔"**
   机制存在，但 upsertDaily 与订单 version CAS 同事务、订单行锁串行化，两个并发事务只有一个能提交，**已提交的丢失更新不会发生**；实际影响为冲突重试消耗。降级为 P2 防御性改进（FUN-03）。
4. **【修正】B-P1-5"批量行情在 Redis 故障时不再降级读 DB"**
   batchQuotes 恒读 DB、从不走缓存；真正故障点是限流切面无降级（INF-01）。缓存读路径（get/布隆）的降级是完善的。
5. **【修正】A-28"updateStatus 无事务"**
   单条 UPDATE 本身原子，"无事务"不是核心缺陷；核心是状态变更不触发撮合（并入 MAT-01）与撮合使用陈旧股票快照（并入 CAC-02）。另：A-37 的表名应为 **reconcile_diff**（非 recon_diff）。
